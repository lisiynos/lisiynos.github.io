# AGENTS.md

Guide for AI coding agents working in this repository. Written for: AI agents editing the site and the maintainer.

## What this is

A static, Russian-language course site, "Математические основы программирования" (summer sessions, olympiad training, algorithms). It is served by GitHub Pages from the repository root at https://lisiynos.github.io/. The default branch is `master` (not `main`). Commit and push to `master`.

There is no build step for the pages: they are hand-written HTML. Two exceptions: the session plan tables (`sN/index.html`) and `search-index.json` are generated (see below).

## Layout

| Path | What it is |
|------|------------|
| `s1/` … `s6/` | Course sessions. `index.html` is the generated session plan. Lesson pages are snake_case `.html` files (a few are `.htm`). A page's assets sit in a folder named after the page (`s2/comb/` for `comb.html`). |
| `dp/` | Design-patterns course pages. Not algorithms. |
| `uts/` | Olympiad training camps (tasks with solutions). |
| `java/` | Java pages. |
| `about/`, `schedule/`, `files/` | Course description, schedule, downloadable files. |
| `common/` | Generator for session plans (`gen.py` and templates), `search_index.py`, `build_navigation.py` (see Navigation), and the tag vocabulary `tags.json` with `build_tags.py` (see Tags). |
| `js/site.js` | Shared script on every page: search, copy buttons and Python run buttons, heading anchors, table of contents, navigation through the course, back-to-top, Rust highlighting. |
| `js/python-worker.js` | The worker that runs the Python run buttons (see Python in the browser). |
| `navigation.json`, `algorithms.html`, `index.html` | Generated by `common/build_navigation.py`: the course data, the algorithm catalogue and the start page. |
| `tags.html` | Generated by `common/build_tags.py`: the index of the tags, with the lessons of each tag (see Tags). |
| `js/index.js` | Recalculates the totals row of the session plan table. |
| `js/viz.js` | Interactive algorithm visualizations (see Visualizations). Plain browser JavaScript, no build step. |
| `style/style.css`, `style/site.css` | Site styles. `site.css` is the responsive and interactive layer and loads after `style.css`. |
| `syntax/` | SHJS syntax highlighter (C/C++, Pascal, Python, Basic, Java, and others). No Rust. |
| `search-index.json` | Generated search index (title, headings and tags with their aliases of every page). |
| `tasks/` | The solutions of the course tasks with their tests, one folder per task (see Solutions and tests). |
| `tests/e2e/` | Playwright end-to-end tests (see Tests). |
| `tests/e2e/fixtures/` | Pages and files that only the tests use. They lie under `tests/`, so they are not site pages: not in the search index and not visited by `pages.spec.js`. |
| `FlashPascal/`, `highlight/`, `plastex/`, `sphinx/` | Vendored third-party code and docs. Do not edit. |
| `audio/`, `.idea/` | Media files and IDE settings. |

## Page anatomy

A lesson page (see `s1/binsearch.html`):

```html
<html>
<head>
    <meta http-equiv=Content-Type content="text/html; charset=utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>…</title>
    <link rel="stylesheet" type="text/css" href="../style/style.css">
    <link rel="stylesheet" type="text/css" href="../style/site.css">
    <script type="text/javascript" src="../syntax/sh_main.min.js"></script>
    <script type="text/javascript" src="../syntax/sh_cpp.min.js"></script>   <!-- one per language used -->
    <link type="text/css" rel="stylesheet" href="../style/sh_nedit.css">
    <script>
window.MathJax = {tex: {inlineMath: [['$', '$'], ['\\(', '\\)']]}};
</script>
    <script async src="https://cdn.jsdelivr.net/npm/mathjax@4.1.3/tex-chtml.js"></script>
    <script src="../js/site.js" defer></script>
</head>
<body onLoad="sh_highlightDocument();">
<div id="content">
    <h1>Title</h1>
    <ul class="tags"><li><a href="#">Tag</a></li></ul>   <!-- a label from common/tags.json, see Tags -->
    <p>Text with inline formulas $O(\log n)$.</p>
    <h3>Section</h3>
    <p><strong>Реализация на C++</strong></p>
    <pre class="sh_cpp">…code…</pre>
</div>
</body>
</html>
```

Pages under `s*/` use `../`; pages one level deeper (`s2/olymp/`) use `../../`. Keep the include order: stylesheets, then the highlighter, then MathJax, then `site.js`.

Session plan pages (`sN/index.html`) also load jQuery 4.0.0 and `../js/index.js`, and have a `<table id="plan">`.

## Rules

- **HTTPS only.** Browsers block `http://` scripts, stylesheets and frames on the https site, so formulas and scripts silently break. Never write `http://` in a `src` or `href` of a resource (plain `<a href>` links may stay http). Protocol-relative `//host/...` is acceptable only if the host serves https.
- **Libraries in use**, all from jsDelivr (`cdn.jsdelivr.net`) at one pinned version each: MathJax 4.1.3 (`tex-chtml.js`, configured in `window.MathJax`), jQuery 4.0.0 (session plan pages only), highlight.js 11.12.0 (`@highlightjs/cdn-assets`, loaded by `site.js` on pages with a Rust block and by `s2/fp_lisp.html`), Pyodide 314.0.7 (loaded by `js/python-worker.js`, see Python in the browser). Do not reintroduce MathJax 2 or 3, jQuery 1–3, `cdn.mathjax.org`, highlight.js 8 to 11.9, Yandex.Metrika, VK widgets or Flash.
- **Images:** `<img loading="lazy" decoding="async">`. Keep the `width` and `height` attributes.
- **Encoding:** UTF-8. Some older pages were Windows-1251; convert a page to UTF-8 before editing it.
- **Code blocks:**
  - Python: `<pre class="sh_python">`
  - C++: `<pre class="sh_cpp">`
  - Rust: `<pre><code class="language-rust">`
  - Pascal, Java and others: the matching `sh_*` class.
  - HTML-escape code: `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`. Code must never contain `</pre>`.
  - Each implementation has a heading paragraph: `<p><strong>Реализация на Python</strong></p>` (or `… на Rust`, `… на C++`).
- **Algorithm examples:** every example is a complete program, prints a deterministic demo, and is verified before it goes into a page:
  - C++: `g++ -std=c++17 -Wall -Wextra -Werror -O2`
  - Rust: `rustc --edition 2021 -D warnings -O` (run with `mise exec -- rustc`)
  - Python 3: standard library only, following the KISS and DRY rules in the global guidance.
  - Check against a brute-force reference on random inputs, not only the demo output.
- **Generated files:** do not hand-edit `sN/index.html` plan tables, `search-index.json` or `tags.html`. Change the source (the session script and `common/gen.py`, or the page) and regenerate.

## Search index

`search-index.json` is built from every page by `common/search_index.py`. Run it after adding, renaming or retitling a page, or changing a tag:

```
python common/search_index.py       # needs beautifulsoup4 and lxml
```

The E2E suite fails if a page is missing from the index or the index lists a page that no longer exists.

## Tags

`common/tags.json` is the one vocabulary of the tags. Each entry has a `label`, which a lesson writes in its `<ul class="tags">`, and `aliases`: other spellings of the same tag that already occur in the repositories, including the raw tags of the problems in `problems_ln` (`tools/find_by_tag.py` there reads this file). No spelling may name two tags.

To add a tag, add an entry to `tags.json`. To rename one, change the label in `tags.json` and in every lesson that uses it. Then run:

```
python common/build_tags.py     # checks the tags of every lesson, writes tags.html
python common/search_index.py   # the index holds the aliases, so a search for an alias finds the lesson
```

`build_tags.py` stops with `tags missing from common/tags.json` when a lesson uses a label that the vocabulary does not have. On a lesson, a tag links to `tags.html?tag=<label>`, and `js/site.js` marks that section of the tag index.

## Session plan generator

`common/gen.py` builds `sN/index.html` from the templates in `common/` and per-session data (for example `s1/parse.py`). It uses Windows-only paths (`'..\\common\\'`), so it does not run on Linux as written. Either run it on Windows or fix the paths first.

## Tests

End-to-end tests use Playwright, with Node 22.23.4 pinned in `mise.toml` (`/root/.local/bin/mise` on this machine; `mise` is not on `PATH` by default).

```
mise exec -- npm install                        # once
mise exec -- npx playwright install chromium    # or PW_CHANNEL=chrome to use an installed Chrome
mise exec -- npm test                           # serves the repo on 127.0.0.1:4399 and tests it
BASE_URL=https://lisiynos.github.io mise exec -- npm test   # tests the deployed site
```

Specs in `tests/e2e/`:

- `pages.spec.js`: every page loads, with no JavaScript errors, no same-site 4xx responses and no `http://` resources. Hard-coded `http://` in `script`, `link`, `img`, `iframe` tags fails the test in every mode.
- `formulas.spec.js`: no raw `$…$` text is left after MathJax runs, and MathJax reports no `mjx-merror` boxes.
- `session-index.spec.js`: plan links resolve and the totals row equals the sum of the lesson rows.
- `interactive.spec.js`: search, copy buttons, table of contents, heading anchors, search index completeness.
- `python.spec.js`: a Python block runs and shows its output (also without a final newline, and nothing of it leaks into the next run), shows the input box without running at the first click of a program that reads input and runs it at the second, reads the input box and raises `EOFError` past its last line, starts the name of an output file on its own line after output without a final newline, shows output, errors and stderr as text and never as HTML, runs the program as `__main__`, starts every run with an empty namespace, stops with «Остановить» so that the next run shows only its own output, disables «Запустить» while a program runs, reports a browser without workers and leaves the buttons as they were, and reports a failed download of Pyodide or of the worker script and an uncaught JavaScript error of the program, after each of which the next run works.
- `solutions.spec.js`: every `data-src` block of the site points to an existing file under `tasks/` and holds the fallback link to it (see Solutions and tests). On the fixture page `tests/e2e/fixtures/solutions.html`: a Python and a Pascal block show their files, highlighted exactly once (the markup equals one pass of `sh_highlightElement` over the text), also when the file arrives before the load event, which one test holds back for 1.5 s by delaying the picture `slow.png` of the fixture; an ordinary block is highlighted exactly once; a block whose file is missing keeps its link and gets the class `solution-missing` without a JavaScript error; the copy button copies the loaded text; «Запустить» shows the input box at the first click and runs the loaded `sum.py` with its input and output files at the second; a file that a program reads holds the text of the input box; a file the program did not close is shown too; and no file of a run stays for the next run.
- `tags.spec.js`: a tag link opens its section of `tags.html`, a search for an alias finds the lessons with that tag, and every tag used on a lesson has a section in `tags.html`.
- `policy.spec.js`: viewport tag, `site.js` and `site.css` included, lazy images, no retired libraries, counters or Flash.
- `known-issues.js`: defects that come from files missing from the repository (absent pictures, Word-export formula markup). The specs fail on any new problem and on any entry that no longer occurs. Remove an entry when its defect is fixed.

`tests/e2e/serve.js` is a small static server for the repository. It needs no Python.

## Visualizations

The interactive pictures run in the reader's browser on GitHub Pages. The code is ready-made static JavaScript in `js/viz.js`, loaded with `<script src="../js/viz.js" defer></script>` after `site.js`. Nothing is built or served at run time, and the picture itself loads nothing from a CDN. The rest of the site loads its libraries from jsDelivr, see Rules.

To place a picture, put a placeholder where it belongs in the lesson text:

```html
<div class="viz" data-viz="longarith"></div>
```

The available names are `longarith` (long addition, multiplication and division, with editable numbers), `fft` (multiplication of two short numbers through the FFT, the numbers as polynomials and the complex values on the plane), `sort` (bubble and selection sort), `binsearch` (binary search), `graph` (breadth-first and depth-first traversal), `bipartite` (two-colouring of a graph, with a choice of graphs), `matching` (Kuhn's algorithm on the example of the lesson) and `segtree` (the segment tree of s5/segments_tree.html: build, sum on a segment, point update, in the bottom-up form of the page). Each picture runs its algorithm in advance and shows the frames one by one with the buttons «назад», «вперёд», «авто» and «сначала». Keep the algorithm in `js/viz.js` and the explanation in the lesson text. A new picture needs a mount function, an entry in `MOUNTS`, its styles in `style/site.css`, and a test in `tests/e2e/viz*.spec.js`.

Known repository facts: `s1/cpp/assert_demo2.html` is a fragment without `<head>`; `s3/dynamic/dynamic_comb.htm` has broken Word-export formulas.

## Solutions and tests

The solutions of the course tasks are files in `tasks/<task>/`, one folder per task, for example `tasks/aplusb_long/sum.py`. The test data comes from the maintainer's archive of olympiad problems (`/srv/problems_ln` on the server; its tests have no licence of their own). The repository keeps only two or three tests per task: the sample tests of the statement, or the smallest tests that show the task; the full sets stay in the archive and are run there by hand. A solution file is changed only together with its tests. A task folder holds:

- `task.json`: `title`; `input` and `output`, the files the solution reads and writes in its working folder, or `stdin` and `stdout` (the default); `time_limit` in seconds per test (default 2); `compare`: `tokens` (default: the whitespace-separated tokens must match), `exact` (the text must match after trailing whitespace on each line and at the end is removed) or `numbers` (token lists of the same length; two numbers are equal when |a − b| ≤ `tolerance` · max(1, |a|, |b|), with `tolerance` 1e-6 unless `task.json` sets it, compared exactly as rationals, so numbers of any length are fine; the other tokens must be equal as text); `checker`, a Python program of the folder that judges instead of `compare`: it runs as `python3 -I checker input output answer` (absolute paths) in the folder of the test, with the time limit of a test; exit code 0 is OK, 1 is WA, 2 is PE, and the first non-empty line of its standard output is the message. A checker writes to standard output only: one that exits with another code, prints anything to standard error (a traceback, a warning) or runs past the time limit has failed, which is an ERROR of the task (see the verdicts); `solutions`, settings of single solution files, which must exist: their own `input`, `output` and `expect`, the verdict the file must get (`{"sum_wa.pas": {"expect": "WA"}}`; OK for every file without one).
- `tests/`: the pairs `NN` (input) and `NN.a` (expected answer), `NN` a number of any width, run in numeric order.
- The solution files: every `.py`, `.cpp`, `.c`, `.pas`, `.java` or `.rs` directly in the folder, except the checker.

`tests/code/check_solutions.py` builds every solution in its own folder (C and C++ with `-O2`) and runs it on the tests, each in a clean folder, until one fails. The verdicts are OK, WA, PE (the output differs as text but not as numbers, or the output file is missing), RE, TL, CE and ERROR: a broken task (no tests, an input without its `.a` file, bad `task.json`) or a failed checker. A solution passes when its verdict equals the expected one; no solution is expected to get ERROR, so it always counts as a failure. The exit code is 1 when a solution does not pass or a task is broken. `--workdir DIR` builds in `DIR` instead of a temporary folder, `--tasks-dir DIR` checks the tasks of another folder. Locally:

```
python3 tests/code/check_solutions.py                 # every task
python3 tests/code/check_solutions.py aplusb_long     # the named tasks
```

The GitHub Actions workflow `.github/workflows/solutions.yml` runs the same command on every push to `master`, on every pull request and by hand (`workflow_dispatch`), in the container `stden/compilers` (g++, Free Pascal, OpenJDK, Python). It writes a table of the verdicts to the job summary and puts an `::error` annotation on every failure: on the solution file that does not get its expected verdict, or on `task.json` of a broken task.

A page shows a solution with a block that loads the file at run time, so the lesson shows the very file the tests run, and one file can be shown on several pages:

```html
<pre class="sh_python" data-src="../tasks/aplusb_long/sum.py"><a href="../tasks/aplusb_long/sum.py">sum.py</a></pre>
```

The link inside is the fallback: the reader sees it without JavaScript and when the file cannot be fetched, for example from a page opened as a file; the block then gets the class `solution-missing`. `loadSolutions()` in `js/site.js` fetches the files of all such blocks at once and puts the text in after the window load event, because `<body onLoad>` runs `sh_highlightDocument()` and a block must be highlighted once; it then highlights the block with SHJS by its `sh_<language>` class (`sh_highlightElement`), so the page loads that language file as for any other code block. The copy button and the «Запустить» button read the loaded text, and a Python solution that reads and writes files runs in the browser with those files: the first click shows the input box, whose text is the content of the input file, and the second runs the program (see Python in the browser).

## Python in the browser

Every `<pre class="sh_python">` block gets a «Запустить» button (`addPythonRunners()` in `js/site.js`). The program runs in the worker `js/python-worker.js` with Pyodide 314.0.7, CPython 3.14 compiled to WebAssembly, which is loaded from jsDelivr on the first run, so a lesson loads nothing extra until a reader runs a program. The output appears under the block, as text and never as HTML. The input box holds the lines that `input()` reads, one line per call; a call past the last line raises `EOFError`. The panel with the input box and the output is in the page from the start, hidden until the first click on «Запустить». A program whose code reads input (`input(`, `sys.stdin` or `open(` in its text, checked at the click) is not run by that first click: the click only shows the panel and puts the cursor in the input box, so the reader types the input before the program asks for it, and the second click runs the program. A program that reads nothing runs at the first click. The output element is a `<div class="python-output">`, not a `<pre>`, so it is not a code block and gets no copy button. The program runs as `__main__`, so `if __name__ == '__main__':` blocks run, and every run starts with an empty namespace. «Остановить» terminates the worker, which ends a program that never finishes, and one program runs at a time. The worker stays a module worker (`{ type: 'module' }`), because Pyodide 314 cannot load in a classic worker. If the browser cannot start the worker, or Pyodide cannot be loaded (usually a network failure), the block shows the reason and the next run starts a new worker. The output reaches the block as the program writes it, with or without a final newline, and nothing of it stays for the next run. An uncaught JavaScript error raised by the program (for example through `js.eval`) ends the run with «Программа завершилась с ошибкой» and the next run starts a new worker. A program that calls `os._exit()` leaves the button on «Выполняется…» until «Остановить» is pressed.

Files: the worker finds the literal names the program opens, `open('sum.in')`, `open('sum.out', 'w')`, `open('x', 'r', encoding=...)`. Before the run it writes the text of the input box to every name opened for reading; after the run it shows every file opened with `w` or `a` (also one the program did not close) under a line `--- sum.out ---`, which starts on its own line also when the output before it has no final newline, and removes the files, so nothing stays for the next run. Because such a program opens a file, its first click only shows the input box (see above), and the box is the content of every file it reads. A name built at run time (`open(sys.argv[1])`) or a path with a slash is not found, and the standard streams are restored after a run that replaced `sys.stdin` or `sys.stdout`.

The runner calls Pyodide directly; PyScript is not used. A Python example still has to meet the rules above: it runs as shown, uses the standard library only, and its output matches the text.

## Navigation

`common/build_navigation.py` builds the course navigation. Run it after changing a session plan (`sN/index.html`), a lesson title or the algorithm list:

```
python common/build_navigation.py
```

It writes `navigation.json` (the lessons of each session in plan order, with previous and next links, and the algorithms of every page), `algorithms.html` (the catalogue) and `index.html` (the start page). It also adds `id` attributes to the headings the catalogue links to, and the `<div class="viz">` placeholders listed in `VIZ`. It is idempotent.

`js/site.js` reads `navigation.json` on every page: a trail «Курс › сессия › страница», links to the previous and the next lesson, and a box «Алгоритмы на этой странице» with links to the sections. A lesson that is not in a session plan gets only the algorithm box, if it has one.

To add an algorithm, add an entry to `ALGORITHMS` with the pages and a regular expression for the heading of its section. The heading must exist; the script stops with `heading not found` otherwise. A section (h2, h3) is preferred to the page title (h1). To add a category, add it to `CATEGORY_ORDER`. The tests are `tests/e2e/navigation.spec.js`.

## Git

- Work on `master`. Commit with a short imperative subject and a body that explains why.
- Stage only the files of the task. The repository is shared and may contain other people's unrelated changes.
- Do not commit `node_modules/`, `test-results/` or `playwright-report/` (they are in `.gitignore`).
