Гибкая методология разработки (Agile software development, agile-методы) - серия подходов к разработке ПО, ориентированных на использование итеративной разработки, динамическое формирование требований и обеспечение их реализации в результате постоянного взаимодействия внутри самоорганизующихся рабочих групп, состоящих из специалистов различного профиля.

XP – Экстремальное программирование: принципы, особенности

Экстремальное программирование (Extreme Programming, XP) - одна из гибких методологий разработки программного обеспечения. Авторы: Кент Бек, Уорд Каннингем, Мартин Фаулер и др.

Основные приёмы:

  • Короткий цикл обратной связи (Fine scale feedback):
    • Разработка через тестирование (Test driven development)
    • Игра в планирование (Planning game)
    • Заказчик всегда рядом (Whole team, Onsite customer)
    • Парное программирование (Pair programming)
  • Непрерывный, а не пакетный процесс:
    • Непрерывная интеграция (Continuous Integration)
    • Рефакторинг (Design Improvement, Refactor)
    • Частые небольшие релизы (Small Releases)
  • Понимание, разделяемое всеми:
    • Простота (Simple design)
    • Метафора системы (System metaphor)
    • Коллективное владение кодом (Collective code ownership) или выбранными шаблонами проектирования (Collective patterns ownership)
    • Стандарты кодирования (Coding standard or Coding conventions)
  • Социальная защищенность программиста (Programmer welfare):
    • 40-часовая рабочая неделя (Sustainable pace, Forty hour week)

В XP особое внимание уделяется двум разновидностям тестирования:

  • тестирование модулей (unit testing);
  • приёмочное тестирование (acceptance testing).

Разработчик не может быть уверен в правильности написанного им кода до тех пор, пока не сработают абсолютно все тесты модулей разрабатываемой им системы. Тесты модулей позволяют разработчикам убедиться в том, что их код работает корректно. Они также помогают другим разработчикам понять, зачем нужен тот или иной фрагмент кода и как он функционирует. Тесты модулей также позволяют разработчику без каких-либо опасений выполнять рефакторинг (refactoring).

Приемочные тесты позволяют убедиться в том, что система действительно обладает заявленными возможностями. Кроме того, приёмочные тесты позволяют проверить корректность функционирования разрабатываемого продукта.

Для XP приоритетным является подход TDD (Разработка через тестирование, Test Driven Development) - сначала пишется тест, который не проходит, затем пишется код, чтобы тест прошел, а уже после делается рефакторинг кода.

Работа с Git

Git - распределённая система контроля версий (см. Системы контроля версий). У каждого разработчика есть полная копия репозитория со всей историей, поэтому коммиты делаются локально, без сервера, а обмен коммитами с другими разработчиками идёт отдельными командами push и pull.

Изменение проходит три места: рабочую папку, где файлы редактируют, индекс (staging area), куда команда git add отбирает изменения для следующего коммита, и репозиторий, куда git commit записывает новую версию. Скомпилированные файлы *.class в репозиторий не добавляют: их перечисляют в файле .gitignore (строка *.class), и git status перестаёт их показывать.

Работа с репозиторием в папке проекта:

git config --global user.name "Имя Фамилия"   # один раз: автор коммитов
git config --global user.email "you@example.com"
git init                            # создать репозиторий в текущей папке
git status                          # какие файлы изменены и какие не отслеживаются
git add HelloWorld.java .gitignore  # добавить изменения в индекс
git commit -m "Первая программа"    # записать версию в историю
git log --oneline                   # история, по строке на коммит
git diff                            # изменения, ещё не добавленные в индекс

Работа с общим репозиторием на сервере (адрес репозитория показывает хостинг, например GitHub или Bitbucket):

git clone адрес_репозитория  # скопировать репозиторий с сервера
git push                     # отправить свои коммиты на сервер
git fetch                    # получить чужие коммиты, не меняя своих файлов
git pull                     # получить чужие коммиты и влить их в текущую ветку

Сценарии на проверку e-mail

Сценарий (тестовый случай) - входные данные и ожидаемый результат; здесь это адрес и ответ проверки: принять его или отвергнуть. По TDD сценарии составляют до того, как написана сама проверка: сначала решают, какие адреса должны приниматься, а какие отвергаться, потом пишут код, который проходит все сценарии. На JUnit каждый сценарий становится отдельным тестом (см. Пример модульных тестов на Java).

Правило в примере упрощённое: имя@домен.зона. Имя состоит из латинских букв, цифр и знаков _, %, + и -; домен - из латинских букв, цифр и дефиса. И имя, и домен могут делиться точками на непустые части, зона - не короче двух латинских букв. Полная грамматика адреса в стандартах гораздо сложнее.

  • Верные адреса: обычный адрес, точка и плюс в имени, поддомен, зона из двух букв.
  • Неверные адреса: пустая строка, нет @, два символа @, пустое имя, пустой домен, нет зоны, точка в начале имени, две точки подряд, зона из одной буквы, пробел.

Каждый неверный адрес, кроме пустой строки, получен из верного одним изменением: вставкой или удалением фрагмента. Если проверка пропустит такой адрес, сразу видно, какое правило реализовано с ошибкой. Проверка сделана регулярным выражением (класс java.util.regex.Pattern); метод matches() требует, чтобы под шаблон подходила вся строка, а не её часть.

Реализация на Java

import java.util.regex.Pattern;

/**
 * Сценарии проверки адреса электронной почты
 */
public class EmailCheck {
    // Упрощённое правило: имя@домен.зона
    private static final Pattern EMAIL = Pattern.compile(
            "[A-Za-z0-9_%+-]+(\\.[A-Za-z0-9_%+-]+)*@[A-Za-z0-9-]+(\\.[A-Za-z0-9-]+)*\\.[A-Za-z]{2,}");

    private static final String[] VALID = {
            "user@example.com",
            "first.last@example.com",       // точка в имени
            "user+tag@mail.example.org",    // плюс в имени, поддомен
            "user@example.ru",              // зона из двух букв
    };

    private static final String[] INVALID = {
            "",                             // пустая строка
            "userexample.com",              // нет @
            "user@@example.com",            // два символа @
            "@example.com",                 // пустое имя
            "user@",                        // пустой домен
            "user@example",                 // нет зоны
            ".user@example.com",            // точка в начале имени
            "us..er@example.com",           // две точки подряд
            "user@example.c",               // зона из одной буквы
            "user name@example.com",        // пробел
    };

    static boolean isValid(String email) {
        return EMAIL.matcher(email).matches();
    }

    // Возвращает число сценариев, в которых результат не совпал с ожидаемым
    static int check(String[] emails, boolean expected) {
        int failed = 0;
        for (String email : emails) {
            boolean passed = isValid(email) == expected;
            System.out.println((passed ? "OK   " : "FAIL ") + "\"" + email + "\"");
            if (!passed) {
                failed++;
            }
        }
        return failed;
    }

    public static void main(String[] args) {
        int failed = check(VALID, true) + check(INVALID, false);
        System.out.println("Не пройдено сценариев: " + failed);
    }
}

Дата и время

Для дат и времени в Java есть пакет java.time (появился в Java 8). Его объекты неизменяемы: метод plusDays не меняет дату, а возвращает новую. Месяцы нумеруются с 1.

  • LocalDate - дата без времени;
  • LocalTime - время суток без даты;
  • LocalDateTime - дата и время без часового пояса;
  • ZonedDateTime - дата и время в заданном часовом поясе;
  • Instant - момент времени, отсчитанный от 1970-01-01T00:00:00Z;
  • Duration - промежуток в секундах и наносекундах, Period - в годах, месяцах и днях;
  • DateTimeFormatter - вывод даты в строку по шаблону и разбор строки.

Старые классы java.util.Date и java.util.Calendar встречаются в существующем коде. Их объекты изменяемы, а месяцы в Calendar нумеруются с 0 (январь - 0), поэтому легко ошибиться на месяц. Старый SimpleDateFormat нельзя без синхронизации использовать из нескольких потоков, а DateTimeFormatter неизменяем, и один его объект можно использовать в любом потоке.

Текущую дату возвращает LocalDate.now(). В примере даты заданы явно, чтобы вывод не зависел от дня запуска.

Реализация на Java

import java.time.Duration;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.Period;
import java.time.format.DateTimeFormatter;
import java.time.temporal.ChronoUnit;

public class DateTimeDemo {
    public static void main(String[] args) {
        LocalDate start = LocalDate.of(2024, 2, 27); // месяцы нумеруются с 1
        LocalDate later = start.plusDays(3); // 2024 год високосный: есть 29 февраля
        System.out.println(later); // 2024-03-01
        System.out.println(later.getDayOfWeek()); // FRIDAY
        System.out.println(start); // объект не изменился: 2024-02-27

        LocalDate end = LocalDate.of(2024, 12, 31);
        System.out.println(ChronoUnit.DAYS.between(start, end)); // 308
        System.out.println(Period.between(start, end)); // P10M4D: 10 месяцев 4 дня

        DateTimeFormatter format = DateTimeFormatter.ofPattern("dd.MM.yyyy HH:mm");
        LocalDateTime begin = LocalDateTime.of(2024, 9, 2, 9, 30);
        LocalDateTime finish = begin.plus(Duration.ofMinutes(90));
        System.out.println(begin.format(format) + " - " + finish.format(format));
        // 02.09.2024 09:30 - 02.09.2024 11:00

        LocalDate parsed = LocalDate.parse("01.03.2024", DateTimeFormatter.ofPattern("dd.MM.yyyy"));
        System.out.println(parsed.equals(later)); // true
    }
}

Потоки в Java

Поток (thread) - последовательность команд, которая выполняется независимо от других потоков того же процесса. Куча у всех потоков программы общая, а стек у каждого свой. Программа начинает работу в главном потоке main.

Поток в Java - объект класса Thread. Код потока записывают в методе run(): наследуют класс Thread либо передают в конструктор Thread объект, реализующий интерфейс Runnable. Новый поток запускает метод start(); прямой вызов run() выполнит код в текущем потоке, и нового потока не будет. Метод join() ждёт завершения потока, после него результаты потока видны тому, кто ждал.

Порядок, в котором выполняются потоки, не определён. Поэтому в примере потоки только считают, а печатает главный поток после join(), и вывод всегда один и тот же.

Реализация на Java

// Поток, который суммирует числа от from до to
class Summer extends Thread {
    private final long from;
    private final long to;
    private long sum;

    Summer(String name, long from, long to) {
        super(name);
        this.from = from;
        this.to = to;
    }

    @Override
    public void run() {
        for (long i = from; i <= to; i++) {
            sum += i;
        }
    }

    long getSum() {
        return sum;
    }
}

public class ThreadsDemo {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("Главный поток: " + Thread.currentThread().getName());
        Summer first = new Summer("first", 1, 500_000);
        Summer second = new Summer("second", 500_001, 1_000_000);
        first.start(); // run() выполняется в новом потоке
        second.start();
        first.join(); // ждём, пока поток завершится
        second.join();
        System.out.println(first.getName() + ": " + first.getSum());
        System.out.println(second.getName() + ": " + second.getSum());
        System.out.println("Всего: " + (first.getSum() + second.getSum()));
    }
}
